## 分析：9/9 饱和——但这次的"没问倒"揭示了关键机制

### 为什么回归地雷没引爆：可运行的测试套 = agent 的自验证 oracle

flash 三次都写出了精确的 `start > end`（而非踩雷的 `>=`）。transcript 层面的原因
不神秘：**fixture 自带可运行的测试套，agent 每次改完就跑 npm test**——即使初稿
写错边界，"not ok 2 - 单点区间 3-3" 会当场把它打回去。编辑→测试→修复的闭环在
3 文件小项目上只需 6 轮，15 轮预算绰绰有余。

**定论：任务自带快速 oracle 时，变更类任务对 flash 同样饱和。**
回归风险的本质区分度来自 oracle 的【缺失、缓慢或不完备】——
小而全的测试套恰恰是最舒适的场景。

### 三套件区分度审计的最终图景（xhard → rule-first → mut）

flash + 真 bash + 快速可自验的任务 = ~95% 通过率，无论只读还是变更。
经全部实验确认的真实区分维度只有四个：
1. **letter-vs-spirit 规则遵从**——已被 rule-precedence 纪律解决（7/10→10/10）；
2. **轮次预算 × 任务规模的张力**（import-list 在 t8/t15 的表现差）；
3. **能力边界附近的语义滑坡**（qwen 档，verifier 的主场）；
4. **基建鲁棒性**（error 重试、MCP 自愈——已修）。

**小尺度任务设计这条路已挖尽。** 剩余的区分度前沿只有一个方向：
**规模压力**——几十文件的变更/聚合、慢 oracle（测试要跑几分钟）、
不完备 oracle（测试覆盖不到的行为靠 verifier 兜）。

### 套件价值定位（并非白做）

mut-* 三案 + 防作弊三层判定（回归/探针/测试防篡改）+ 8/8 双向自检的 checker，
是 harness 自身的【回归套件】：将来任何 prompt/工具/编排改动若伤了"变更纪律"
（比如诱发改测试凑通过、边界修复变糙），mut-* 会第一时间报警。
