# 借鉴清单：他山机制的决策台账

> 这份文件的存在理由是**约束**，不是扩张。同类 harness（Claude Code / Cursor / Codex /
> Warp / Cognition / OpenHands）公开的机制越来越多，看完一圈的自然冲动是"这个也加、那个也加"。
> 本文把每一条机制变成一次**记名决策**：借、变形借、还是不借，理由与判据写在借之前。
>
> 它不是路线图（路线图是 `docs/08-maturity-optimization-checklist.md`），也不是研究结论
> （结论是 `docs/05-findings.md`）。它是这两者之间的**准入闸门**：一条外来机制要进 docs/08
> 的编号队列，先在这里拿到一个结论行和一份判据。

---

## 1. 这份文件是什么 / 怎么用

### 1.1 借鉴的五条规矩

**① 借问题不借代码。** 被借的对象是"这个机制回答了哪个设计问题"，不是实现。
Claude Code 的源码是专有的；本文所有关于它的描述都来自公开论文与官方文档
（`arXiv:2604.14228` 分析的是**公开可得的 TypeScript 源码**快照 v2.1.88），
社区反编译重建（如 `sidbharath.com` 的解剖文）只作**行为参考**，不作实现依据、不抄结构。
判断标准：我们的实现要能从我们自己的 `docs/03-interfaces.md` 推导出来，
而不是从别人的文件名推导出来。

*为什么不那么做*：直接照搬文件结构会同时继承对方的部署假设。
Claude Code 是绑定单仓库的短命 CLI 进程，OpenClaw 是常驻守护进程，
Hermes 是单个长命 Python 进程（论文 §10 的三方对照）——同一个设计问题在三种进程拓扑下
有三种正确答案。我们是"CLI + Web 宿主 + Electron 壳"的第四种，抄谁的形状都不对。

**② 判据先于实现。** 每条待借机制在动手前必须写出**可测指标 + 阈值**。
这是 `docs/05-findings.md` 已有的纪律（"判据先写"），在借鉴场景下尤其重要：
外来机制自带别人的成功叙事，没有我们自己的判据，验收就会退化成"看起来装上了"。
本文 §4 的条目模板把这一条做成必填项。

**③ 旗标默认关，有证据再翻默认。** 新借的机制一律 env 旗标 + 默认关闭，
与 `AGENT_COMPACT_SUMMARY`（MEM-01 Phase B）、`AGENT_MODEL_PROBE`（MODEL-01b）同款。
翻默认需要的是本仓库的实测数字，不是对方的发布公告。

*为什么不那么做*：默认开会让确定性评测（`eval/deterministic.ts` 13 场景）
的被测对象悄悄变成"机制 + harness"而不是 harness。我们已经三次栽在
"残留环境变量把测试指向真端点"上，仪器纪律不能因为借了新东西就松。

**④ 不稀释自己的长处。** 四条硬不变量，任何借来的机制不得触碰：

| 不变量 | 具体含义 | 为什么它是长处 |
|---|---|---|
| **hooks 不得绕过 verifier 只读** | 外部 handler 不能给核查者放行写类命令，也不能改写核查者的工具面 | 核查者的公信力全部来自"全新上下文 + 只读"这个结构事实（`docs/05-findings.md` §4） |
| **分类器不得高于硬拒** | 任何自动判定只能在"人工审批"这一档上省人力，不能推翻既有 deny / 圈禁 / SAFE-01~03 的拒绝 | 与 Claude Code 的 `hard_deny > soft_deny > allow > 用户意图` 同向，且我们的硬拒有 12 条 SSRF / 符号链接逃逸负例测试背书 |
| **子代理回摘要不回正史** | 派生的子执行者只把结论与产物引用交回父上下文 | 与论文 §8.3 的 sidechain 同结论；我们的编排层"逐直接依赖交接"已是这个语义，动态 spawn 不得退化 |
| **诚实持久化** | 借来的任何恢复/压缩机制，界面与台账必须能说出"这一份是原文 / 是摘要 / 是未知" | 我们花了整轮修"界面说谎"（V-04 族）；压缩的可观测性是我们相对成熟产品的少数优势之一 |

**⑤ 连失败一起借。** 一条机制的公开失败史与它的设计同等重要，本文条目必须记入。
已收录的三桩：

- **沙箱网络围栏的解析器差异**（论文 §5.4 脚注，证据等级 Tier C）：
  主机白名单用 JavaScript 后缀匹配，而域名解析在**内嵌 null 字节处截断**，
  于是构造出的主机名能通过后缀检查却解析到另一台被禁主机。
  影响范围 v2.0.24–v2.1.89（含被分析的 v2.1.88 快照），**未分配 CVE**。
  → 教训：白名单的"匹配语义"必须与"使用语义"由同一个解析器产生。
  我们 SAFE-03 的 DNS 双验与每次重定向重验是同一族防线，
  但 `isReadOnlyCommand` 的引号感知扫描（案例 #7 修）正是同类差异的近亲，
  借 hooks / 分类器时要重查一遍。
- **AgentJacking（Tenet Security）**：工具返回值是**不可信输入**。
  Sentry DSN 按设计是公开的且接受任意 error 载荷，攻击者 POST 一条带 markdown 指令的事件，
  渲染成假的 "Resolution" 段；开发者让 agent 去看这条 issue，
  agent 经 MCP 拉回污染内容当作修复建议，跑了攻击者的 npm 包并外传 AWS / GitHub / SSH 凭据。
  **对 Claude Code、Cursor、Codex 均已确认，含沙箱变体与 CI/CD**。
- **GhostApproval（Wiz）**：仓库里放一个名为 `project_settings.json` 的符号链接，
  实际指向 `~/.ssh/authorized_keys`；审批对话框显示的是诱饵名字，用户批准的是另一处写入。
  Amazon Q / Cursor / Antigravity 已修，Augment / Windsurf 承认未修，
  Anthropic 认为超出威胁模型不予认定——**这个分歧本身要保留着读**，它争的是"知情同意从哪来"。
  我们 SAFE-02 已覆盖符号链接/junction 逃逸，SAFE-04 已把授权绑定到规范化 input hash；
  但 GhostApproval 打的是**审批文案**而不是路径检查，
  提示我们审批卡应显示"解析后的真实目标"而不只是模型给的参数。

配套的 **Willison 批评**必须与 §2 的分类器行一起读：
分类器数字（下文）**把误操作与刻意的提示注入混在一起**，
而分类器无法可靠阻止注入；**耐久的修法是不给数据、不给工具**，不是相信自动放行。
这条批评直接决定了本文对分类器的结论是"变形借且带前置"而不是"借"。

  "用户批准约 **93%** 的权限提示"——那是**审批疲劳**的证据，
  不是分类器准确率；两个数字讲的是两件事。
- **`4% / 7%`**（Cursor Auto-review：约 4% 的动作被拦、约 7% 的会话最终打扰到人）：同上，转述，未直读。

  **规则写成自然语言散文而非正则**、
  **分类器读 `CLAUDE.md` 但从不读共享的 `.claude/settings.json`（签进仓库的配置不能给自己授权）**：
  出自官方 `Configure Auto Mode` 文档，经转述，未直读。
  但**论文正文可交叉印证其机制方向**：`CLAUDE.md` 内容被缓存给分类器使用
  （`setCachedClaudeMdContent()`，为避免加载器与权限系统的循环依赖），
  且 `CLAUDE.md` 是以 **user 消息**而非 system prompt 下发的，
  因此"模型遵从是概率性的，确定性执行层是 deny-first 权限规则"——
  这条**指导 vs 执行的刻意分离**已由 B 级证据坐实。
- **压缩连败的量级**（1,279 个会话撞上 50+ 次连续压缩失败、单会话最高 3,272 次、
  折合每日 250K 次白烧 API 调用；修法是"连续失败 3 次即停"的一个常量）：
  仅见于 `sidbharath.com` 的逆向解剖文，**未在论文或官方文档中交叉印证**。
  数值不可引用，但"压缩必须有连败熔断"这个**结构结论**我们照借（见 §4.1 之外的 §2 第 1 行）。
- **OpenHands 的"每 run 一容器"**：论文只说 SWE-Agent / OpenHands
  依赖 Docker 容器隔离**整个执行环境**（对比 Claude Code 的分层策略执行），
  "每 run 新建容器"这一具体生命周期本轮**未核实**。

## 2. 对照现状表

读法：**差距**列只有三种取值——`已有`（我方已有对等或更强实现）、
`部分`（有骨架缺关键面）、`无`。**结论**列的"变形借"一律附带变形的理由。

|---|---|---|---|---|---|

### 4.1 A1 工具面（**正在实施中**，不由本文宣告完成）

- **它回答什么设计问题**：模型能看见的工具集合应当由谁、在什么时机收窄？
- **状态**：**同期由另一条线实施中**，产出见 `eval/a1-tools-report.md` 与 `src/tools/**`、`src/presets.ts`、README 工具表的同期改动。本文只登记结论（§2 第 6 行：借），**不代其宣告完成，也不复述其判据**——避免两处声明同一件事。
- **本文唯一附加要求**：装配期预过滤若落地，`run_config` / `/api/harness` 必须报出**本 run 实际下发的工具名单**而不是包声明的名单。理由是 host-lags 纪律的老账：能力接上了，但"配了没启用"这类状态要能看出来。

### 4.2 最小 hooks（PreToolUse / PostToolUse / Stop）

- **它回答什么设计问题**：委托方要在不改 harness 源码的前提下加一条自己的策略或副作用，从哪进？
- **我们的判据**（先写）：
  1. handler 退出码 **2 阻断**、`0` 放行、**其他任何退出码（含 1）一律非阻断并记一条可见的 hook 错误**——三种退出码各一条行为锁，`exit 1 悄悄阻断` 与 `exit 2 悄悄放行` 两个变异必须各打红一个测试文件。
  2. `PreToolUse` 阻断时，拒绝理由**进正史回喂模型**（与既有 deny 消息同款），且台账新增一行可数事实：`hooks{fired, blocked}`。
  3. handler 超时有上限（默认 5s）且**超时 = 非阻断 + 告警**，不是静默放行、也不是阻断——超时按阻断处理会让一个写坏的 hook 把整轮任务掐死。
  4. 位置锁：`PreToolUse` 在**审批门之前**触发，一条测试钉住"hook 阻断的调用不进审批表"（不合法或已被策略拒的调用不该去打扰人做授权决定——与 `validate-input.ts` 同一条理由）。
  5. 只读隔离锁：核查者谱系（verifier / planner 自答）的工具调用**不经外部 hooks**。
- **默认开关**：`AGENT_HOOKS_CONFIG`（指向配置文件；不设 = 整个机制不存在，零开销、零事件）。翻默认的条件：不翻。这是委托方显式配置才该存在的东西。
- **不得触碰的不变量**：§1.1 ①（hooks 不得绕过 verifier 只读）——本条由上面判据 5 直接实现；§1.1 ②（hook 的 `allow` 不能推翻既有 deny / 圈禁 / SAFE-01~03），照借论文里那条"PreToolUse 的 allow 不绕过后续 deny"。
- **实施顺序位置**：D3（权限三档）**之后**。理由：hooks 的第一个真实用途就是"补一条 deny 规则"，deny 档不存在时它会被迫承担权限系统的职责，那是错的层。
- **为什么不做更多**：不做 27 事件（把别人的子系统清单当需求）；不做 `prompt` / `http` / agentic verifier 三种 handler——`prompt` 与 agentic 会变成第二条模型调用路径，其成本、延迟、不确定性全都进不了我们的台账与 trace，而"每一笔 token 有归属"是 OBS-01/02 的地基。

### 4.3 deny-first 权限规则 + manual/plan/auto 三档预设（backlog D3）

- **它回答什么设计问题**：审批疲劳下，人的注意力应该花在哪一小部分动作上？
- **对方的证据**：用户批准约 **93%** 的权限提示（论文 §5 引 Hughes 2026，B 级）——逐动作确认作为唯一安全机制**在行为上不可靠**；他们的回应不是加更多警告，而是**重构问题**：划定边界让 agent 在界内自由跑。这一条与我们"修环境 > 提示词"同源。
- **我们的判据**（先写）：
  1. `deny` 档进 `ToolPermission`：**deny 压过 allow，即使 allow 更具体**——一条"宽 deny + 窄 allow"用例钉住求值顺序（并与 Omnigent"更严的规则先查"同向）。
  2. 三档预设**只捆既有开关，不新增机制**：manual = 审批门逐次问 + run 内同工具同参数放行；plan = `mode=plan` + 计划确认门；auto = 审批 auto。一条测试逐档比对**捆的开关值集合**。
  3. **界面不许说谎**：装配条继续显示展开后的真实开关值，模式名不得替代它（V-04 族）——一条渲染锁 + 一个"只显示模式名"的变异打红。
  4. 台账记 `permissionMode` 与该 run 实际发生的 `approvals{asked, auto, denied}`。
- **默认开关**：默认 `manual`（= 今天的行为，零语义变化）。翻默认要本仓库的数字：held-out 上 auto 档的有害动作率与人工档的对照。
- **不得触碰的不变量**：§1.1 ②；SAFE-01 的"pack 泛化 `auto` 不能盖掉 server 单工具 `ask`"必须继续成立（已有测试）。
- **实施顺序位置**：本文所有条目的**第一顺位**，且是 4.2 / 4.4 的前置。第一步按 backlog D3 的原话——**先写清三档各捆哪些开关的对照表，再动 UI**。
- **为什么不做更多**：不做七档；不做 `bypassPermissions` 等价档（我们的 `--yes` 已是它，且圈禁与硬拒不受其影响，这个性质要保住）。

### 4.4 分类器辅助审批（**前置未满足，不得开工**）

- **它回答什么设计问题**：`auto` 档里，哪些动作可以不打扰人？
- **对方的证据与它的裂缝**：1,053 人测试中人工复核抓出注入危险命令 **13.6%**、分类器 **89%**，有害动作率 6.3% → 2.4%（**未核实**，C 级）；Cursor 的形态是**分类器跑在 agent 循环内部**而非独立端点，被拦时**把解释回给父 agent**，后者常能安全绕行而完全不打扰人——约 **4%** 动作被拦、约 **7%** 会话最终打扰到人（**未核实**）。**裂缝**：Willison 指出这个对比把误操作与刻意的提示注入混在一起，而分类器阻止不了注入；耐久的修法是**不给数据、不给工具**。
- **硬前置（未满足前不得开工）**：**先有危险命令注入评测集**——一批"看起来像正常任务但会诱导出危险命令"的用例，进 held-out 或独立套件，先量出**我们现在**的拦截率与误拦率。没有这个基线，分类器上线后无法区分"它在拦"和"它在乱拦"，而误拦的代价我们已经付过：核查饥饿式的 fail-closed 曾烧掉 22 轮零写入的返工。
- **我们的判据**（先写）：① 误拦率上界（在既有 25 条 `ho-*` 上新增拦截数必须为 **0**——那些用例全是正当任务）；② 注入集上的拦截率下界（基线定出后再写死数字，本文不预填）；③ **优先级锁**：一条测试钉住"分类器的 allow 不能推翻任何 deny / 圈禁 / SAFE-01~03 的拒绝"，即 `hard_deny > soft_deny > allow > 用户意图` 的我方等价物；④ **配置不能给自己授权**：照借那条刻意的排除——分类器可读指导性文件（我们的 `AGENT.md`，见 §4.7），**不得读签进仓库的权限配置**；⑤ 拦截即路由信号：拒绝理由回喂模型（与 4.2 判据 2 同款），台账记 `classifier{evaluated, blocked, overriddenByRule}`。
- **默认开关**：`AGENT_APPROVAL_CLASSIFIER=0`。翻默认需要判据 ①②③ 全部达标 + 一轮真实运行对照。
- **不得触碰的不变量**：§1.1 ②（永不高于硬拒）；§1.1 ①（不得给核查者放行）。
- **实施顺序位置**：D3 之后、且**排在注入评测集之后**。在 docs/08 里应作为 SAFE 系的新 ID 立项，不塞进 SAFE-04。
- **为什么不做更多**：不做两阶段快筛 + 思维链的完整形态（先要基线）；不做投机式竞速（对方 `BASH_CLASSIFIER` 拿预启动的分类结果与超时赛跑）——那是为交互延迟优化的，我们连准确率基线都还没有。

### 4.5 动态子代理 `spawn_task`

- **它回答什么设计问题**：执行途中才发现需要一条独立的调查支线时，怎么开？
- **我们的判据**（先写）：① **回摘要不回正史**——一条测试钉住父上下文只增加"结论 + 产物引用"，子代理正史落独立档案（我们的 `.agent-run-history/` 天然支持，与 sidechain 同构）；② 预算从父 run 的执行谱系**扣减**，不另给额度（否则 `AGENT_TOTAL_TOKEN_BUDGET` 的口径又要打一个洞）；③ 深度上限（默认 1，即子代理不得再 spawn）+ 并发上限沿用 `AUTO_CONCURRENCY_CAP=3`；④ 资源标签继承（子代理不得绕过 `DomainPack.resources` 的独占互斥——双探针场景会当场炸）。
- **默认开关**：`AGENT_SPAWN_TASK=0`。翻默认需要：至少一个真实案例里它比"多一轮对话"更省（墙钟或 token 二者之一）。
- **不得触碰的不变量**：§1.1 ③；verifier / planner **不得** spawn（自答审批不入门那条防死锁纪律的同族）。
- **实施顺序位置**：AGENT-02 的最小切片，排在本文所有 SAFE 系条目**之后**。理由：动态派生会放大隔离缺口，SAFE-05 的 Windows 面还开着。
- **为什么不做更多**：不做 supervisor / mailbox / cancel / 重新分派（AGENT-02 全量，暂缓）；不做 worktree 隔离（归 SAFE-05 / AGENT-03）。**成本提醒写在条目里**：对方 plan 模式下 agent team 约 7× token，而我们自己的数据说单领域任务上编排是纯开销——这条机制的默认答案应该是"不用"。

### 4.6 Windows WSL2 沙箱后端（SAFE-05 缺口）

- **它回答什么设计问题**：主开发机是 Windows 时，执行隔离从哪来？
- **现状缺口**：`ExecutionBroker` 的加固面很长且 Linux CI 13 个真实逃逸 canary 全绿（#33461119575），**但本机 Windows OCI 全部 skipped**——也就是说日常开发的那台机器上，`required` 档实际拿不到隔离。held-out 的 `ho-workdir-escape-denied` 三次通过**靠的是模型自律**（report 模式下 bash 无圈禁），这已在 docs/08 与交接页里记为"不是圈禁证据"。
- **技术选择**：走 **WSL2**，与 Zed 的 Windows 选择一致（macOS Seatbelt / Linux bwrap+namespaces / **Windows WSL**）。**不自建沙箱**——Codex 团队自建免提权沙箱是因为要覆盖所有 Windows 用户（含没有 Windows Sandbox 的 Home SKU），我们是单操作员且 WSL2 本机可得；他们否掉的两条路对我们同样成立且更省事地避开：Windows Sandbox 是一次性 VM（要在真实 checkout 上干活），完整性级别标记会把工作区变成全机低完整性写入池。
- **我们的判据**（先写）：① 现有 13 个 OCI canary 在 WSL2 后端上**逐条真跑不 skip**（skip 数必须为 0，这本身就是本条的验收）；② UID / rootfs / cgroup / 网络 / 读写-改名-删除 的双层 canary 与 OCI 后端**同一份断言**（不许为新后端写一套更松的）；③ `required` 档在 Windows 上失败时**绝不 host fallback**（既有性质，加一条平台专属锁）；④ 跨边界路径映射（`D:\...` ↔ `/mnt/d/...`）有专门负例——路径归一化已经坑过我们两次（默认工作目录过不了自己的白名单）。
- **默认开关**：`AGENT_EXEC_ISOLATION` 沿用既有三档，Windows 上默认仍 `report`。翻到 `required` 需要判据 ①②③④ 全绿。
- **不得触碰的不变量**：不得为了让 Windows 通过而放宽任何既有断言；Zed 那条教训照记——**只靠指令约束不够**（他们用一次符号链接置换攻击演示，与 GhostApproval 同一课）。
- **实施顺序位置**：SAFE-05 Phase 2 的第一刀，优先于本文其余 SAFE 条目（它是 4.4 / 4.5 的安全前置）。
- **为什么不做更多**：不做每 run 独立 UID / worktree（SAFE-05 完成定义的其余部分，另算）；不做云端一次性沙箱（Modal/E2B/K8s——单操作员形态没有这个需求）。

### 4.7 分层 `AGENT.md` 指令文件

- **它回答什么设计问题**：领域纪律与项目约定放在哪，才能不改代码就改、且可审阅可进版本控制？
- **现状缺口**：四个领域包的纪律活在 `src/presets.ts` 的字符串里，改一条要发版。而"领域包纪律两条腿"（自身失败复盘 + 公开参考设计蒸馏）本就是持续增补的东西。
- **层次设计**（对齐对方四级去掉 managed）：`~/.agent/AGENT.md`（用户全局）> 项目 `AGENT.md` / `.agent/rules/*.md`（签进代码库）> 子目录按需。**不做 `/etc` 全机策略级**——那属多用户治理，与非目标一致。
- **我们的判据**（先写）：① 以 **user 上下文注入**而非 system prompt（照借对方的结构选择），并在启动行与 `run_config` 报出**实际加载了哪几个文件**；② 文档与界面必须写明**这是指导不是执行**——遵从是概率性的，确定性靠权限规则与圈禁（对方把这条"指导 vs 执行的刻意分离"讲得最清楚，B 级证据）；③ 加载量有上限且超限**明确截断并告警**（指令文件会长，任务首条 user 消息目前永不压缩，放任会直接吃掉窗口）；④ 与 `DomainPack.systemPrompt` 的**优先级写死并测试**：包 prompt 是冻结的领域契约，`AGENT.md` 只能补充不能推翻其中的纪律条款。
- **默认开关**：文件不存在 = 机制不存在。存在即加载（这一条不设旗标——它的开关就是文件本身，与"纯文本、可审阅、可进版本控制"的初衷一致）。
- **不得触碰的不变量**：§1.1 ②——`AGENT.md` **不得**声明任何权限；若将来上分类器，它可读 `AGENT.md` 但**不得读权限配置**（§4.4 判据 ④ 的另一半）。这正是对方那条刻意排除的价值所在：签进仓库的配置不能给自己授权。
- **实施顺序位置**：可与 D3 并行（互不依赖），但**不早于** EXT-01 的 manifest 讨论——两者都在回答"包的声明面往哪放"，方向要先对齐。
- **为什么不做更多**：不做 LLM memory scan（自动往记忆里写结论——我们的 MemoryStore 是显式工具写入，这个性质要保住）；不做检索式记忆（换掉的是可审阅性，MEM-02/03 另议）。

### 4.8 pack manifest（EXT-01）

- **它回答什么设计问题**：领域包怎么带版本、权限声明、依赖与来源地发布，而不是硬编码进 `src/presets.ts`？
- **格式选择**：**对齐 Agent Plugins 1.0 的 `plugin.json`**（一个 manifest 打包 `skills/` + `mcp.json`，跨厂商，技术委员会来自 Amazon / Cursor / Microsoft / OpenAI / Vercel，VS Code / Copilot CLI / Copilot app 首日支持）。**不自造格式**——跨厂商标准已是既成事实，自造一份只会让我们的四个领域包永远出不了这个仓库。
- **我们的判据**（先写）：① manifest 里的权限声明**只能收窄不能扩权**（一条"manifest 声明 auto 但 server 声明 ask → 仍 ask"的测试，与 SAFE-01 既有性质同款）；② 版本不兼容**启动即失败**（fail-closed，与两条 context env 的非法值同款：CLI 退出码 1、Web 建宿主即抛）；③ 来源与完整性：本地路径外的来源必须有摘要校验（照 REL-01 的供应链口径，不为包破例）；④ 现有四个包**原样迁移零行为变化**——迁移前后同一份 held-out 子集结果逐条相同，这是本条的主验收。
- **默认开关**：`PACKS` 硬编码路径继续可用；manifest 加载为附加来源。翻默认（硬编码退役）需要判据 ④ 达标。
- **不得触碰的不变量**：§1.1 ②（manifest 不得扩权）；§1.1 ①（manifest 不得改核查者的只读约束或白名单语义——`verify.readOnlyCommands` 可声明，但"禁重定向/链式/命令替换"的判定归 harness，不归包）。
- **实施顺序位置**：EXT-01，排在 §4.7 之后（先对齐"声明面往哪放"）。
- **为什么不做更多**：不做签名与启停 UI（EXT-01 完成定义的其余部分，等真有第三方包再说）；不做 skills 目录（§3 已定不借）；**不做远程来源**（EXT-02 暂缓，且 AgentJacking 提醒我们先把"工具返回值不可信"做实）。

## 5. 我们已经比他们强的地方

写这一节的用途是**防止自我贬低式乱抄**。读完一篇 200KB 的架构分析，很容易觉得自己什么都缺；
但逐条对照后，下面五项是我们**有证据**领先、且借鉴时最容易被稀释的：

**① 核查作为结构性角色，而不是一种可选的子代理类型。**
对方的 Verification 是六种内置子代理之一；我们的 verifier 是**全新上下文 + 只读硬约束 + 三值裁决
（`passed` / `unverified` / `advisory`）+ 返工闭环**的结构件，且带 A/B 证据链：
强 verifier 真实救回字节级错误且对正确产物零假阴性（`eval/ab-report-strong.md`）；
价值域被两条边界夹住——执行者太强没错可救、失败在预算/基建层救不着，
**主场是能力边界附近的语义错误**（`eval/ab-report-hard.md`）；
fail-closed 的三种误伤形态（裁决解析失败 / 核查预算耦合 / 核查白名单缺失）**已枚举且各有解**；
核查失败的三层归因顺序（**先怀疑规则 → 再怀疑预算 → 最后才怀疑能力**）由三跑受控对照证实
——同一份逐字节相同的产物，15 轮得不出结论、30 轮得出**误判**、30 轮 + 分形态纪律**精确命中真缺陷**。
论文自己把"生成器-评估器分离该放在 harness 内还是外"列为**未决的开放问题**（§12.6 / §13）；
我们已经放在里面并且量过了。**借 hooks / 分类器 / spawn 时，这一条是第一个会被稀释的。**

**② 证据基建。**
L6 运行台账（`src/ledger.ts`，判据 `STRUCTURED_OUTPUT_RULE` 在收数据之前写死）+
held-out 25 条与实现调优**分离** + `eval/stats.ts`（Wilson 95% / 无偏 pass@k / 首轮与修复率 / p50·p95 /
**先写死的 11 值 taxonomy**）+ `eval/deterministic.ts` 13 场景**打编译产物 `dist/`**（不是 `tsx src`——
build 配置一漂，单测照绿而发布件起不来）+ `eval/mock-provider.ts` 双 wire 故障注入 +
`scripts/mutation-smoke.mjs` 变异冒烟。
对照那份行业调查：可观测性采用率近 89% 而离线评测只有 **52.4%**，且**质量而非成本**是投产首要障碍
（Bessemer 估 "78% 的 AI 故障不可见"）——我们做的正是那缺失的一半，
而且变异冒烟直接回答了"你的验收测试在实现被破坏时真会变红吗"这个几乎没人量的问题。

**③ 多厂商与降级。**
`src/model-fallback.ts` 是 L0 装饰器（上面几层只见 `ModelClient` 接口）+ 逐端点熔断，
且**负向路径才是主场**：认证失败 / 400 **原样上抛不降级**（换端点救不了配置错误，
只会把同一个 401 打到第二家去并掩盖真因）、跨端点重发**剥掉 thinking 块**（签名属于上一家）、
全链熔断报错而不静默返回空。降级链**只包主执行者**——
verifier / planner / vision 三角色不进链，因为"核查者应 ≥ 执行者"是设计约束，
静默换端点会让它在无人知晓时失效。对方是单厂商自家模型，这些问题不存在也就没有答案。

**④ 诚实持久化语义。**
`sameRunResume=false` 会照实说；归档明确不能续跑且到处照实说；
`fallbackChain` 的 `null`（这台机器上没有这条防线）与 `[主端点]`（配了链但只有一环）**必须分开记**；
窗口"不认识就不猜"（registry 每条带出处，未知就是未知，不画那一段水位）；
压缩占位符带 `excerpt:` 原文首行摘录 + 台账记 `compaction{proactive,reactive,droppedBlocks,collapsedTurns}`。
对照对方自陈的"压缩对用户基本不可见"（论文 §12.4）与外部研究指出的两项额外代价
（摘要步是**阻塞式推理停顿**，且**非确定性**——同一输入跨次运行保留的内容会浮动），
这一条是我们**主动选择付复杂度换来的**，不是还没做到。

**⑤ 硬件与 EDA 领域闭环。**
STM32 真机 HIL（跨进程探针锁、镜像自校验固件、芯片系列常量这类**编译器/静态检查/单测全都管不了、
真机是唯一裁判**的缺陷）+ KiCad 双判官（`kicad-cli sch erc` / `pcb drc --schematic-parity`）
+ 结构化 host-kit。这不是"也支持硬件"，而是**把"判官"从测试套件扩展到物理世界**：
案例 #8 里 verifier 独立连板读出与我完全相同的寄存器证据（`0x4002381C = 0x00008000`）并据此拒签。
纯软件 harness 没有这一层，也就无从发现"核查预算按软件域定的 15 装不下硬件域"这类结论。
