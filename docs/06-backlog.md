## 零、一条反复出现的规律（排查时先想它）

**harness 早就有能力，Web 宿主没接。** 这一系列里出现了 **五次**：

| 能力 | 早就在 | 宿主接入轮次 |
|---|---|---|
| 会话正史 `result.messages` | 一直返回 | R6a |
| thinking 块 | `model-client.ts:41` 显式开了 adaptive | R6b |
| 多轮续跑 `runContinuation` | `loop.ts:99`，为返工 inherit 建的 | R8 |
| 角色模型 `verifierModel`/`plannerModel` | CLI 从 env 装配 | R9 |
| 并行编排 `runPlanned` | v1.1 就有 | R7 |

**接手启示**：遇到"这个功能没有"，先去 `src/` 找一遍再动手写。这个 harness
比它的宿主走得远得多。

**2026-08-07 补两例，规律要改写**：

| 能力 | 早就在 | 状态 |
|---|---|---|
| 文本流式 `text_delta` | R2 就改成了 SSE 命名通道 | 前端 `app.js:216` 一行直接丢弃（AC2-06 那次跑实测 **1133 条 delta 在流**）|
| `api_retry.backoffMs` | 本轮刚加 | reducer 白名单投影当场丢掉，**加字段的同一个提交里就发生了** |

第二例说明这不只是"旧宿主落后于新 harness"——**只要 harness 加字段而不同时接
宿主，缺口就即刻生成**。前端 reducer 是按事件类型逐字段白名单投影的，任何新字段
默认被丢，且不会有任何报错。所以纪律不是"回头补"，而是：

> **harness 加一个字段 = 同一个提交里把宿主那一侧一起接上，并加一条渲染锁。**

本轮那条锁（`test/ui-patch.test.ts` 的"重试退避等待在界面上可见"）就是这么抓到
自己刚造的缺口的——肉眼看不出来，因为界面并不报错，只是少显示一行。

## 二、契约执行（建议优先，两项是同一件事的两面）

现状是：**声明了契约，但不执行它**。两处现场：

### 2.1 结构化输出（最高优先）

`verifier` / `planner` 现在靠「解析 → 失败重问一次 → 再失败 fail-closed」。
`src/verifier.ts:86` 的注释本身就是证据——项目已经撞上过并打了补丁：

> fail-closed 直接返工会对正确产物空转（A/B 实测烧 10 万级 token），一次重问便宜得多

**正解是让它不发生**：Anthropic 用 `tool_choice: {type:"tool", name:"..."}`
强制工具调用，OpenAI 兼容端用 `response_format: json_schema`。
这能基本消灭 `VERDICT_PARSE_FAIL`——**D3 三种 fail-closed 误伤形态的第一种**，
不是推测收益，是消灭一个已命名、已实测、界面上已专门告警的失败模式。

注意 compat 端点未必都支持 `response_format`，需要能力探测 + 降级回现有解析路径。

### 2.2 工具入参 schema 校验 —— ✅ 已实施（2026-08-07）

落地：`src/tools/validate-input.ts`（`validateToolInput`）+ `ToolExecutor` 在
**审批门之前**统一拦（`src/tools/registry.ts:111`）。23 条单测。不引入 zod/ajv。

三条实施时才看清、值得记下的东西：

1. **MCP 是硬理由，不是风格偏好**。`src/mcp.ts:75` 把外部 server 声明的 schema
   原样 `as JSONSchema` 收下，`execute` 再把 `input ?? {}` 直接转发——那些工具
   **没有任何位置可以手写检查**。而 `mcp.json` 里 stm32 是 `permission: "auto"`，
   含 `write_memory` / `flash_firmware`。手写路线从结构上盖不住 MCP。
2. **早有一处现场在等这一层**。`src/model-client-openai.ts` 的 `safeParseArgs`
   注释写着「解析失败回传空对象，**让工具的输入校验层**给出可操作报错」——
   代码一直在向一个从未建成的层交接。今天残缺 JSON 会以
   `{__malformed_arguments: "..."}` 原样转发给 MCP server。
3. **失败开放是这个校验器的核心纪律**，比查得严重要。只在【认得的构造被明确
   违反】时拒绝；`oneOf`/`anyOf`/`$ref`/未知 type 一律放行，也**不**强制
   `additionalProperties`。理由：schema 来自外部服务端，"看不懂就拒"是亲手造出
   fail-closed 那一类新失败模式——项目已有三种误伤形态的教训。required 缺失
   检查已经能抓到拼错的键名（错误消息会把实收键名一并列出）。

**审批门之前**是有意的：入参就不合法的调用不该去打扰人做授权决定。

各工具自己的 `typeof` 检查**保留**：`Tool.execute` 是可直接调用的公开面（测试
就这么用）。分工是——这一层执行【声明过的 schema】，工具那层管 schema 表达不了
的语义约束（非空、必须 `https://`）。

**真机验证**：deepseek-v4-pro 走 Web 宿主完整跑一轮，26 次真实工具调用穿过
校验器零误拒，run 正常收尾（这一层坐在每次工具调用的热路径上，单测全绿不足以
说明它不误伤）。

**未做**：`parseVerdict` / `parsePlan` 的手写字段校验是同一类问题的第二个现场，
校验器已可复用，但裁决 JSON 的形状约束与工具入参不同（需要的是"缺字段时如何
降级"而不是"拒绝"），值得单独想清再动。

## 三、重试与降级（小改动，有新触发条件）

**已有且做得不错的部分**：两层重试（SDK HTTP 重试 + loop 层 `errorRetries`），
配 `api_retry` 事件可观测；`isTransientApiError`（`model-client.ts:60`）做了
错误分类——auth/permission/404/400/422 永久性不重试，429/连接超时才重试。
这已经是 Tenacity 的 `retry_if_exception_type` 那一层。

**两个缺口**：

1. ~~**退避无抖动**~~ **✅ 已实施（2026-08-07）**：`backoffWithJitter`
   （`src/loop.ts`）用**等量抖动**——`ceiling/2 + random*ceiling/2`，不是全抖动。
   全抖动取 `[0, ceiling]`，有可能几乎立刻重试，而 429 是服务端明说"你太快了"，
   立刻重发是错误响应；等量抖动保证至少等到一半，同时给出 2:1 散布窗口，
   对 `AUTO_CONCURRENCY_CAP=3` 足够拉开三条轨。

   **两条实施笔记**：
   - 纯函数测试覆不住调用点——把 `loop.ts` 改回线性，那 4 条纯函数测试照样全绿。
     另加了一条走 loop 的行为锁（20 次重试的等待不全相等），反向自检立即失败。
     为此给 `api_retry` 事件加了 `backoffMs`（抖动后等待不再是定值，界面只显示
     "第几次重试"会让人以为退避固定）。
   - **加字段时当场又撞上第零节那条规律**：`app.js` 的 reducer 按字段白名单投影
     事件，`backoffMs` 在那一层就被丢掉了——harness 发了、宿主半路扔。是 UI 静态锁
     抓到的，不是肉眼。**新字段落地时就要连宿主一起接**，否则它自动变成下一条
     "harness 有、宿主没接"。
2. **无模型降级**：V-30 建好角色模型框架之后，"执行者失败降级到备用模型"
   变得很便宜。

**明确不做**：可组合的重试策略 DSL、熔断器。按 P2「按需晋升」，
没有实测需求就不该建，分类这一层已覆盖真实场景。

## 五、人机协作（原语都在，只是没人用）

### 5.1 计划确认门 —— ✅ 已实施（2026-08-07）

`runPlanned` 的 `onPlan` 本来就是 await 的（`orchestrate.ts`），
文档字符串写着"宿主可展示计划、做人工把关"——**harness 侧零改动**，
缺的一直只是宿主接这条线。

落地：`POST /api/runs` 收 `planGate`（**默认关**，逐 run 显式开）→ `onPlan` 里
`await waitForPlanDecision(run)` → `POST /api/runs/:id/plan-approval` 应答 →
`plan_approval_request` / `_resolved` / `_expired` 三条 durable 合成事件。

四个设计决定：

1. **默认关**。宿主也被脚本化驱动（eval、契约测试、无人值守）——默认阻塞会把
   那些场景全部挂死，而"挂死等人"正是 V-01 修掉的那类失效。
2. **挂起点在第一个子任务发射之前**，所以否决 = 零副作用地停下。这正是签字位
   该在的位置（真机实测：门挂起时事件来源只有 `host` / `planner`）。
3. **否决不是 error**：`stopReason = "plan_rejected"`、`run_end.outcome = "rejected"`，
   徽章"计划未获批准"（warn 不是 bad）。混进 error 界面会显示"异常终止"，
   那是对委托方自己的决定说谎（V-04 的教训）。
4. **挂起态归 ActionRail，已决/过期归 Plan 面**——同一条不在两处重复展示（V-16）。
   收尾时必须宣告过期并解除挂起，否则编排协程永远吊在 onPlan 里。

**只做批准/否决，不做"否决 + 反馈 → 重新规划"**：那需要把反馈喂回 planner
并重跑，是另一个设计（且与 §5.2 的判据问题耦合），值得单独一轮。

**真机验证**（deepseek-v4-pro，浏览器点击）：否决 → 零子任务执行、徽章
"计划未获批准"、全页无"异常终止"字样、Plan 面留下"✗ 计划被否决 · 时间 ·
一个子任务都没有发射"；批准 → 签字位退出待办区、状态保持运行中、直播条随即
显示子任务的工具调用。axe 另加一条挂起态扫描——这是**阻塞式**交互，
键盘/读屏用不了它等于整个运行卡死。

**顺带修掉一个先于本功能就存在的缺陷**（真机验证时撞出来的，见第八节）。

### 5.2 需求澄清（`ask_user` 工具）

没有机制让 agent 提问并等待，但 `approval_request` 就是"阻塞等人"的原语，
加一个 `ask_user` 工具即可复用那条通路。

**与哲学高度契合**：`SubTask.acceptance` 已经存在，H1 讲的是"把主观判断降维为
可程序化条款"。需求澄清正是人这一侧的同一件事——**开跑前把验收标准问清楚，
比事后靠 verifier 抢救便宜得多**，这正是 B5 那条「修环境 > 提示词 > 事后核查」
的优先级排序。

**但要先想清判据**：什么时候该问、问几个。容易做过头，值得单独设计一轮。

## 七、环境与纪律（接手必读）

- **浏览器窗格**：截图通道在本会话始终不可用（窗格未显示、页面不合成帧）。
  `resize_window` 传显式宽高能拿到真实视口；**强制元素宽度不会触发媒体查询**，
  测窄屏必须用真实视口。窗格偶发整体无响应，`preview_start` 可重开。
- **rAF 陷阱**：隐藏标签页不触发 `requestAnimationFrame`。已在 `core/batch.js`
  处理并有常驻测试，但任何新的帧调度都要记住这条。
- **停后台实例**：Windows 上 `taskkill /PID <pid> /T /F`，停完必须验证端口已释放
  （见记忆 `windows-taskstop-node-zombie`）。
- **改文件用 Write/Edit 工具**，不要用 PowerShell 的 `Set-Content -Encoding utf8`
  （会写 BOM，破坏 tsx 解析 JSON）。
- **Python heredoc 改代码要当心转义**：本会话多次因 `\n` / `\\` 被吞而写出语法
  错误。改代码优先用 Edit 工具。
- **验证纪律**：能行为验证就不要字符串断言。本会话最有价值的几次验证都是
  "让脚本化模型真的去读它收到的东西"——正史有没有带上、图有没有送到，
  都是让对方模型的**回答内容**取决于事实，而不是断言字符串。
- **排查 UI 先确认自己观察的时机**（2026-08-07 踩到）：验文本流式时第一轮
  "失败"其实是我在 run 结束后才点开它——`ensureSubscription` 对终态 run
  按设计不订阅，行为完全正确。先看时序，再怀疑代码。

## 八、真机验证撞出来的既有缺陷（2026-08-07）

**编排模式下客户端在 planner 结束时就收摊。**

`ui/public/app.js` 的 `applySegmentDone` 有条快路径：非核查模式下 `done` 即判
整个 run 终止。它不限定来源，而**编排模式下 planner 自己那一轮也发
`done(completed)`**。于是客户端在 planner 一结束就把状态置为 done，控制器随即
`es.close()`——之后的 `plan` / `plan_result` / 子任务进度 / `run_end` 全部收不到，
界面停在"已完成"，还把 planner 的 JSON 当执行者报告展示。

- **触发条件**：`mode=plan` 且未勾"开启独立核查"——**选了"计划编排"之后的默认组合**。
  勾了核查则 `state.verify` 为真、快路径不生效，所以此前的浏览器实测没撞上。
- **它就是 V-01 那条「段终止 ≠ run 终止」**。当时在事件层修过（`done` 只记段，
  run 级收敛由 `run_end` 宣告），**reducer 侧漏掉了同一条**。
- **修法**：快路径限定 `source === "main"`；planner 与 `sN/main` 的 done 不终止 run。
  三条回归锁（planner done / 子任务 done / 单跑 done）。
- **怎么发现的**：做 §5.1 的真机验证时，服务端明明是 `plan_rejected`，界面却显示
  "已完成"。把服务端事件拉下来**在页面里用同一份 reducer 重新 reduce 一遍**，
  得到的状态是对的——于是判定不是 reducer 错，是实时投递断了。这个"重放对比
  live"的手法值得留用：它一步就把"派生逻辑错"和"事件没收到"分开了。

**教训**：一条修在 A 层的纪律，要回头查它在 B 层有没有同构的漏网。
V-01 修的是服务端事件语义，reducer 是另一处同样需要它的地方。

## 九、案例 #8 产出的需求（2026-08-07，真实任务驱动）

全案见 [`docs/cases/case-08-crc-selfcheck-hil.md`](cases/case-08-crc-selfcheck-hil.md)。
STM32 真机跨域交付（`stm32-coding` → `stm32-debug`），计划确认门首次用于
真实高风险场景（下一步就写 Flash）。

**已修**：Web 宿主根本没接 MCP——`ui/server.ts` 连 `src/mcp.js` 都没 import，
`AGENT_UI_MCP=1` 只改状态快照文案，于是 `stm32-debug` 这类全 MCP 工具面的包
在 Web 宿主下等于废的。第七个"harness 有、宿主没接"，也是最大的一个。

### 9.1 核查预算不可按领域覆盖 —— ✅ 已实施（2026-08-07）

`src/verifier.ts` 的 `VERIFIER_MAX_TURNS = 15` 是写死常量，`DomainPack` 无法覆盖。
案例 #8 里 `stm32-debug` 的**执行者**有 40 轮护栏，**核查者**只有 15 轮——
而真机核查每条 AC 都要多次探针往返。两轮 verifier 都跑满 15 轮、都从未写出裁决，
最终消息是半截工具调用 → 解析失败 → 重问找不到结论 → fail-closed。

**这是发现 6 的误伤形态②（核查预算耦合）在新领域复现。** 当初的修法是把核查预算
与执行者**解耦**（固定 15）；本案例说明**解耦还不够——15 是按软件域定的数，
硬件域装不下**。

**加重情节**：verifier 不是在空转。它读了 `image_size`/`image_crc32`，然后
`debug_until` 到 CRC 代码附近、`read_memory` 读 `0x08000140`——**它已经嗅到
CRC=0 这个真缺陷并在追查**，是预算把一次正当调查掐断了。预算不足的代价不只是
"没结论"，而是"把已经走对方向的核查掐死在半路"。

**落地**：`DomainPack.verify.maxTurns` → `VerifiedRunOptions.verifyMaxTurns` →
`VerifyOptions.maxTurns` → `runVerifier`；缺省导出为 `DEFAULT_VERIFIER_MAX_TURNS = 15`。
优先级 env（`AGENT_VERIFY_MAX_TURNS`，非法值退出码 1）> 包 > 默认。
`stm32-debug` 设 **30**——依据是案例 #8 那次核查在第 15 轮时已完成 5/6 条验收
并在追查第 6 条，约需一倍余量收口；同时**不高于它自己 40 轮的执行者护栏**
（核查者比执行者还能跑说明护栏的相对关系没想清楚，有一条测试锁住这个不等式）。
编排下**逐子任务按各自的包取**：s1(coding) 与 s2(debug) 的核查工作量差一个量级，
共用一个数就是案例 #8 那个失效。

**行为锁而非字段锁**：让脚本化 verifier 直到第 24 轮才收口 → 缺省 15 轮下落
fail-closed，给到 30 轮拿到实质裁决。写这条时踩了两个坑，都记下来：
① 收口点初设在第 18 轮，被**重问机制**（maxTurns 3）恰好救回——那是重问在按设计
工作，不是预算够用，所以收口点必须 > 15+3；② 脚本模型是全局计数器，**返工轮**
会越过收口点让第二轮核查立刻通过，得关掉返工才测得准。

**顺带**：`/api/harness` 的 `verifierBudgetTurns: 15` 是写死的、UI 还写着"固定"，
这两处在改完之后都变成了谎话——同提交接上，并加了来源标注（默认/包/env）。
接的过程中**第三次踩到字段白名单投影**：`run_config` 的 reducer 分支不列出新字段
就静默丢弃，是那条渲染锁抓到的。加字段必查三处：reduceEvent 投影分支、
派生函数、渲染分支。

**未做**：9.2 兜底裁决带过程摘要——它与本项互补（本项让核查跑得完，9.2 让跑不完
时的信号有用），但改的是裁决内容不是预算，单独做。


### 9.2 fail-closed 兜底裁决要带过程摘要

`{passed:false, issues:["核查未产出明确结论"]}` 对返工者零信息量——它既可能是
"核查者胡言乱语"，也可能是"做了大量工作没来得及收口"。案例 #8 是后者，而返工者
拿到的信号与前者完全相同，只能从头再来，又烧光 40 轮。
兜底裁决应带上：跑了几轮、调了哪些工具、最后停在哪。

### 9.3 stm32-debug 的 verifier 无任何计算手段 —— ⏸ **降级：暂不做**（2026-08-08 复议）

该包 `builtinTools: ["read_file","write_file"]`、无 `readOnlyCommands`。
凡"设备自报一个派生量（CRC/校验和/哈希）"的验收，verifier 只能确认读到了，
不能独立推导对不对——这类项本该走诚实降级进 `unverified`。
做法二选一：补一条最小只读计算白名单（如 `node <仓库内参考脚本>`），
或在包文档里明确把这类验收归入"必须委托方复核"。

### 9.4 工具名幻觉：MCP 前缀漏写

verifier 调用了 `read_variable`（正确名 `stm32__read_variable`）。
`ToolExecutor` 回"Unknown tool + 可用工具清单"，不致命但每次白烧一轮。
候选：错误消息里对相近工具名做一次最短编辑距离提示。

### 9.5 明确不做

- **芯片系列常量的静态检查**：`1u << 6` vs `1u << 12` 这类错误编译器、静态检查、
  单测全都管不了，真机是唯一裁判。这不是 harness 该解决的问题——**它恰好是
  verifier 的主场**（能力边界附近的语义错误），本案例里 verifier 差一点就抓到了。
  正解是把 9.1 修好让核查跑完，而不是加一层猜芯片型号的检查。

### 9.6 真机域的"只读核查"必须含"把系统带到可观测状态" —— ✅ 已实施（2026-08-08）

用 30 轮预算重跑 s2 时暴露的，比 9.1 更根本（全案见案例 #8 第四点五节）。

verifier 的核查规则第 1 条是「只读核查：不要修改、创建或删除任何东西」。
软件域的只读核查天然完整——文件就在那里，读就是了。**硬件域不是**：
被观测对象必须处于运行态才有意义，而"复位并运行目标"不是持久修改，
却长得像修改。于是纪律良好的 verifier 会避开它。

实测：重跑那次 verifier 68 次工具调用里只用过 1 次 `run_for_duration`，
**一次都没用 `reset_target`**。上一段（executor 的 `stop_debug_session`）
把核心留在非运行态，verifier 连上去 `self_check` 一 halt，读到的是未初始化
SRAM（`magic=0x4E0A43C0`、`PC=0x2000002E` 在 SRAM 内），据此判 AC2/AC3 失败。
委托方 `reset run` + 2 秒后读同一块 RAM：magic=TELM、hclk=16000000、
size=532，PC 在 `main()` 里——**固件一直是好的**。

它并没有胡说：advisory 里已经推断出"可能是板子未处于正常运行态、固件本身
可能是正确的"，**只是没去做那个能证实推断的动作**。

**做法（候选，未定）**：
- `VerifyOptions` 增加"可用的状态复位动作"声明（领域包给出，如
  `reset_target` / `flash_and_run`），并在 verifier 提示里明写
  「只读指的是不改产物，不含不许让被测系统跑起来」；
- 或由 executor 负责"交接时把板子留在运行态"（`stop_debug_session` 前
  先 `reset run`），把责任放在交接契约而不是核查者身上。

**前者更正**：责任在核查者——它必须能独立把系统带到可观测态，否则它对
执行者的交接状态有隐性依赖，那正是 fresh-context 核查要消除的东西。

### 9.7 30 轮也不总是够（同次重跑）

返工后的 round 1 仍跑满 30 轮、仍空输出落 fail-closed。9.1 把"从不收口"
改善成"能收口一次"，没有根治——真正卡住它的是 9.6。**先修 9.6 再谈加预算**，
否则只是让一次注定无效的核查跑得更久。

## 十、9.6 的实施与三跑对照（2026-08-08）

**真凶不是泛化纪律，是领域包自己的指令。** `STM32_VERIFY_INSTRUCTIONS` 第 4 条
原文「不要 flash、不要 reset、不要写内存」是一刀切——verifier 不是从泛化的
"只读"推断出不能复位，是**领域包明确禁止了它**。

而这条禁令写得没错，只是**只对一种核查形态成立**：故障现场核查里复位会毁掉
`.noinit` 闩锁 / CFSR / 异常栈帧（案例 #1/#3 的血泪，必须保留）；运行行为核查
恰好相反，不复位就读到上一段会话遗留的未初始化 SRAM。

**所以不是放宽纪律，是把两种形态分开写清楚**（杠杆定律：成文规则冲突用确定性
规则消除，不是靠更强的模型去权衡）：

1. `STM32_VERIFY_INSTRUCTIONS` 显式分叉 (a) 故障现场 / (b) 运行行为，各自给出
   该做什么、为什么，**并给出"怎么认出板子没在跑"的判据**（幻数不对 / PC 不在
   main 相关代码 / 多个字段像随机数）——否则模型只能猜，猜错就把好固件判成假报告。
2. 通用 verifier 提示的只读那条澄清：只读针对【产物】，**不等于"不许让被测系统
   运行"**；具体以领域核查方法为准，**没有领域说明时给出自足兜底**。
   （初版在这里引用了一个不存在的章节，是既有测试当场抓到的。）

**明确不做**：不新增 `DomainPack.verify.stateSetup` 字段。根因在指令文本，加字段
等于把同一件事拆到两处声明。按 P2 按需晋升——等真出现"指令写不下 / 需要程序化
读取"再晋升。

### 三跑 A/B/C（同一份产物，ELF SHA256 三跑逐字节相同）

| | ① 15 轮 | ② 30 轮 | ③ 30 轮 + 分形态 |
|---|---|---|---|
| `reset_target` | — | **0 次** | **2 次** |
| 实质结论 | 无 | ✗ 误判 | **✓ 精确命中真缺陷** |

第三跑独立读到与委托方完全相同的寄存器证据（`0x4002381C = 0x00008000`），
AC5 判失败、AC6 落 `unverified`——正确答案。

**定论**：核查失败要分三层归因，顺序不能颠倒——
①**核查者被成文规则挡住**（本例，改规则）→ ②**预算不够跑完**（9.1，加预算）
→ ③**缺取证手段**（9.3，补白名单）。先怀疑规则，再怀疑预算，最后才怀疑能力。
本例若只加预算（②），得到的是一次跑得更久的错误裁决。

### 9.7 仍开着

第三跑 round 0 依旧跑满 30 轮空输出落 fail-closed，靠返工后的 round 1 才拿到
裁决。**首轮收口仍不可靠**——这条与 9.2（兜底裁决带过程摘要）是同一个现场的
两面，建议一起做。

## 十一、9.7 + 9.2 的实施与四跑对照（2026-08-08）

**9.7 收口续跑**：撞满预算时最终消息往往是半截工具调用、文本为空——原有的
"重问"另起新 loop 只喂原始文本，文本为空时直接跳过，**整场核查连同已取到的
全部证据一起作废**。正解是续跑同一会话（`runContinuation` 带上正史），
要求"别查了，用已有证据下结论"。收口预算 `VERIFIER_WRAPUP_MAX_TURNS = 2`
刻意很小：只允许写裁决、不允许继续取证，大了等于偷偷放宽调查预算。

收口提示明写「没查完的进 unverified、**不得因没查完判 failed**」——否则预算
用尽会直接退化成 fail-closed 第三种误伤形态（案例 #4 为此烧过 22 轮空转）。

**9.2 兜底带过程摘要**：summary 现在带上为什么没收口、多少次工具调用及分布、
最后一条消息片段，并明写"这不等于产物有问题"。零工具调用单独措辞——
"核查很可能根本没有开展"与"查了很多没收口"是两种完全不同的故障，返工策略不同。
`issues[0]` 哨兵原文不动（`isParseFailure` 与界面核查饥饿判定都靠它）。

### 四跑对照（同一份产物，ELF SHA256 四跑逐字节相同）

| | ① 15 轮 | ② 30 轮 | ③ +分形态 | ④ +收口续跑 |
|---|---|---|---|---|
| `reset_target` | — | 0 | 2 | 2 |
| round 0 | ✗ | ✓ 但误判 | ✗ 空输出 | **✓ 19 轮自行收口** |
| round 1 | ✗ | — | ✓ | **✓ 31 轮 = 30 调查 + 1 收口** |

**直接证据是 round 1**：31 轮那一轮的 `unverified` 原文含「**预算用尽**且缺乏
独立 CRC32 计算手段」——正是收口提示要求的措辞；同一位置在第三跑是空输出落
fail-closed。round 0 这次 19 轮就自行收口、未触发续跑，**因此不能拿它当 9.7
的证据**，只能说明这次收敛得快。

### 9.8（新）执行者宿主级失败同样丢掉全部上下文

第四跑首次尝试：执行者跑到第 29 轮 API 超时，`stopReason=error` →
`runVerified` 按既有设计跳过核查直接返回。而它已经做了 **28 次工具调用**、
最后一句是「让我验证 RCC 寄存器布局是否正确」——**正朝着真缺陷去**。
一次瞬时端点故障把整段工作连同进展全部作废，返工从零开始。

**这与 9.7 同构**：9.7 救的是"核查没来得及收口"，9.8 是"执行没来得及交付"。
`runContinuation` 那条通路同样适用（多轮对话、返工 inherit、9.7 收口都在用它）。
候选做法：主 run 因**瞬时**错误终止时（`isTransientApiError` 已能分类），
带着正史续跑一次而不是整段作废；非瞬时错误（认证/4xx）照旧快速失败。

### 9.9（观察项，未判定）verifier 用了 write_memory

第四跑 verifier 用了 5 次 `write_memory`——在写 `RCC_AHBENR` 测试那个位写不写
得进去（`unverified` 里"RCC_AHBENR 写入不生效"就是这么测出来的）。这是很漂亮的
独立取证，但也说明 9.6 那句「只读针对产物」可能比预期放得宽。
**尚未判定是否收紧**：它没有改动交付物，而"写寄存器验证硬件行为"确实是硬件域的
正当核查手段。先记着，等再出现一次不当使用再定。

## 十二、清单收尾（2026-08-08）

### 9.4 未知工具名给最近候选 —— ✅ 已实施

实测形态：verifier 调 `read_variable`，正确名是 `stm32__read_variable`——MCP 工具
带 `<server>__` 前缀，模型容易漏。原来只丢一份全量清单，工具面二十几个时模型得
自己在里面找，每次白烧一轮。

`nearestToolNames` 两条判据按可靠性排序：①**后缀命中**（实测最常见形态，几乎不
误报，优先给）；②**编辑距离 ≤ 名长/3**（拼写手滑，阈值卡紧）。八竿子打不着就
不提示——**猜错方向比不猜更糟**。候选只是提示，全量清单照给。

### 9.3 降级：暂不做（复议理由）

原判断是"补一条最小只读计算白名单"。复议后**不做**，两条理由：

1. **三值裁决已经正确处理了它。** 案例 #8 四跑里，AC6 每次都精确落进
   `unverified` 并注明「无可用的宿主侧 CRC32 独立计算手段」，移交委托方复核，
   委托方（用独立参考实现）完成了比对。**这是诚实降级在按设计工作，不是失败。**
   按 P2 按需晋升——没有实测证明它不够用。
2. **给这个包加计算手段的代价被低估了。** `selectPackTools` 给执行者与核查者
   **同一套工具面**，所以给 verifier 加 bash 等于也给执行者加。而
   `stm32-debug` 刻意不给 bash 是 v1.0 演示换来的：给了 bash，执行者会绕开 MCP
