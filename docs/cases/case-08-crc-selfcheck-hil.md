# 案例 #8 — 镜像自校验固件：计划确认门首次用于真实高风险交付

**日期**：2026-08-07
**领域**：STM32 裸机固件（跨域：`stm32-coding` → `stm32-debug`）
**宿主**：Web 宿主，`mode=plan` + **计划确认门** + `AGENT_UI_MCP=1`
**模型**：deepseek-v4-pro（执行/核查/planner 同模型，compat 路径）
**板子**：STM32L151RC，dev_id `0x427`，Flash 256 KB，ST-Link
**结果**：**s1 通过 / s2 未通过**；交付物 6 条验收中 4 条真机通过、1 条失败、1 条连带失败。
根因已由委托方定位并用受控实验证实。

---

## 一、任务

给案例 #1 的遥测固件加**启动镜像自校验**：链接脚本导出镜像结束符号 →
用 STM32 硬件 CRC 外设算 `[0x08000000, _image_flash_end)` 的 CRC32 →
结果与镜像长度写进遥测结构体末尾。六条验收 AC1–AC6 全部可程序化判定。

任务书里写死了三类硬性禁止（低功耗 / DBGMCU / SWD 引脚重配）——违反任何一条
都可能让板子失联而现场无人。

**AC6 是刻意设计的"查不了"项**：它要求把设备自报的 CRC 与宿主独立算出的值比对，
而 `stm32-debug` 包**没有 bash 工具、没有只读命令白名单**，其 verifier 没有任何
计算手段。任务书为此明写「如果你没有独立计算手段，按诚实降级写进 `unverified`」。

---

## 二、过程

### 计划确认门：签字位第一次用在真实高风险场景

planner 耗时 138 s，产出两个子任务：

| 子任务 | 包 | 依赖 | 资源 |
|---|---|---|---|
| s1 代码改动与构建 | `stm32-coding` | — | — |
| s2 真机烧录与逐条验收 | `stm32-debug` | `s1` | `swd-probe` |

**门挂起时事件来源只有 `host` / `planner`，零子任务发射**——此刻否决是零副作用的。
委托方在浏览器上点「批准并开跑」后 s1 才启动。

计划质量值得记一笔：planner 自己按域切分、给 s2 打上独占资源标签、并且把 AC6 那句
**「或诚实标注 unverified 并注明原因」原样带进了子任务验收**——诚实降级的纪律
传导到了子任务层，不是顶层写完就丢。

### 执行

- **s1**（`stm32-coding`，13 轮，0 返工）：verifier 逐条实证后通过。
- **s2**（`stm32-debug`，21 轮）：烧录成功，执行者自报完成。
- **s2 的 verifier**：跑满 **15 轮**（`VERIFIER_MAX_TURNS`），40 次工具调用，
  **从未产出可解析裁决** → 重问也找不到实质结论 → fail-closed 兜底判 failed。
- **返工轮**：跑满 **40 轮**（`stm32-debug` 包护栏）→ `max_turns`。
- **第二轮 verifier**：同样跑满 15 轮，同样落到 fail-closed 兜底。
- run 以 `error` 收尾，`plan_result.completed=false`。

## 三、委托方独立验收（地面真值）

委托方侧另建独立的 CRC 参考实现（放在工作区之外，agent 看不到），
用 CRC-32/MPEG-2 公认检查值 `0x0376E6E7` 与「字喂入 / 字节喂入」双路径互印证自检。

| 验收 | 期望 | 实测 | 结论 |
|---|---|---|---|
| AC1 构建干净 | 零 error/warning | 532 B flash / 2104 B RAM，`-Werror` 下通过 | ✅ |
| AC2 既有字段 | magic=`0x54454C4D`、hclk=16 MHz、uptime 递增 | `TELM` / 16000000 / 42938→44249（+1311 ms / 实耗 1.3 s） | ✅ |
| AC3 镜像长度自洽 | == `.bin` 字节数且 4 的倍数 | `image_size=532`，`.bin`=532，`_image_flash_end=0x08000214` | ✅ |
| AC4 符号一致 | `symbols_match=true` | true，零段不匹配 | ✅ |
| AC5 CRC 非平凡 | ≠0 且 ≠0xFFFFFFFF | **`0x00000000`** | ❌ |
| AC6 CRC 正确性 | == `0x36338E3F` | `0x00000000` | ❌（连带） |

### 根因（真机取证）

| 取证点 | 实测 | 含义 |
|---|---|---|
| `RCC_AHBENR` @ `0x4002381C` | `0x00008000` | 只有 bit15 FLITFEN；**bit6 写入没生效**，bit12 从未置位 |
| `CRC->DR` @ `0x40023000` | `0x00000000` | 外设无时钟——已使能且复位过的 CRC 应读出 `0xFFFFFFFF` |

`#define RCC_AHBENR_CRCEN (1u << 6)` 是 **STM32F1** 的位号。
**STM32L1 的 `RCC_AHBENR.CRCEN` 在 bit 12**；bit 6 在 L1 上未实现，
写入被硬件丢弃（读回即证）→ CRC 外设始终无时钟 → 写 `CRC->DR` 全部丢弃 →
读回恒为 0。

### 受控确认实验

在交付物的**副本**里只改这一个位号（6 → 12），其余一字未动：

- 重新构建：同为 532 字节
- 独立参考值：`0x7189AAB5`（与原版不同，因为指令里的立即数变了）
- 烧录运行后设备实测：**`0x7189AAB5`——分毫不差**

**结论：agent 的 CRC 设计整体正确**（链接符号、镜像长度、外设时序、按 32 位字
喂入、执行时机全对），**唯一缺陷是这个芯片系列相关的位号常量**。
编译器与任何静态检查都抓不到它——只有真机能。

## 四、产出的 harness 需求

### R1（已在本轮修复）Web 宿主根本没接 MCP

`ui/server.ts` 连 `src/mcp.js` 都没 import，`selectPackTools(pack, POOL, [])`
永远传空表，`AGENT_UI_MCP=1` 只是把状态快照里一句 reason 去掉。
后果：**`stm32-debug` 这类全 MCP 工具面的包在 Web 宿主下等于废的**。
开案例前撞出来，已修（懒连接 + 逐子任务按包收窄 + 真实状态快照 + 关停断开）。
这是第七个「harness 有、宿主没接」，也是最大的一个。

### R2（未做）核查预算不可按领域覆盖

`src/verifier.ts` 的 `VERIFIER_MAX_TURNS = 15` 是**写死的常量**，`DomainPack`
无法覆盖。本案例里：

- `stm32-debug` 的**执行者**有 40 轮护栏；
- 它的**核查者**只有 15 轮——而真机核查的每一条 AC 都要好几次探针往返
  （连板 / self_check / load_symbols / 读多个变量 / 跑一段再读）。

两轮 verifier **都跑满 15 轮、都从未写出裁决**，最终消息是半截工具调用，
解析失败 → 重问找不到结论 → fail-closed。

这是**发现 6 的误伤形态②（核查预算耦合）在新领域复现**。当初的修法是把核查预算
与执行者**解耦**（固定 15），本案例说明**解耦还不够——15 这个数本身是按软件域
定的，硬件域装不下**。建议：`DomainPack.verify.maxTurns`，`stm32-debug` 设 30+。

**加重情节**：verifier 并不是在空转。它读了 `image_size`/`image_crc32`，
然后去 `debug_until` 到 CRC 代码附近、`read_memory` 读 `0x08000140`——
**它已经嗅到 CRC=0 这个真缺陷并在追查**，是预算把一次正当调查掐断了。
预算不足的代价不只是"没结论"，而是"把已经走对方向的核查掐死在半路"。

### R3（未做）fail-closed 兜底把两类失败压成一句话

裁决 `{passed:false, issues:["核查未产出明确结论"]}` 对返工者毫无信息量——
它既可能是"核查者胡言乱语"，也可能是"核查者做了大量工作但没来得及收口"。
本案例是后者，而返工者拿到的信号与前者完全相同，于是它只能从头再来，
又烧光 40 轮。建议：兜底裁决带上**核查过程摘要**（跑了几轮、调了哪些工具、
最后停在哪），让返工者知道上一轮走到哪了。

### R4（未做）stm32-debug 的 verifier 无任何计算手段

AC6 那条本该走**诚实降级**落进 `unverified`。它没走到那一步（先被 R2 掐断），
但设计上的缺口是真的：该包 `builtinTools: ["read_file","write_file"]`、
无 `readOnlyCommands`，凡"设备自报一个派生量（CRC/校验和/哈希）"的验收，
verifier 只能确认读到了，不能独立推导对不对。
建议给该包补一条**最小只读计算白名单**（如 `node <仓库内的参考脚本>`），
或明确把这类验收归入"必须委托方复核"。

### R5（未做）工具名幻觉：MCP 前缀漏写

s2 的 verifier 调用了 `read_variable`（正确名是 `stm32__read_variable`）。
`ToolExecutor` 会回一条"Unknown tool + 可用工具清单"，不致命，但每次都白烧一轮。

## 五、方法学收获

1. **计划确认门的价值恰在"挂起点在第一个子任务发射之前"**。本案例挂起时事件来源
   只有 `host`/`planner`，一个字节都还没写进 Flash——签字位若挪到执行开始之后，
   它就只是个装饰。
2. **委托方的独立参考实现必须先自检再用**。本案例的 CRC 参考实现先过 MPEG-2 公认
   检查值、再用"字喂入 vs 每 4 字节反序后字节喂入"两条路径互印证，然后才敢拿它
   去判 agent 的产物。地面真值本身不可信时，整场验收都是空的。
3. **"只改一处的受控实验"把猜测变成证明**。定位到位号可疑之后，复制一份只改这
   一个常量、重新构建烧录，设备算出的值与独立参考分毫不差——这一步把
   "我们认为唯一的缺陷是位号"升级成了"已证实"。
4. **芯片系列相关的常量是 agent 的稳定盲区**。代码结构、外设时序、算法全对，
   错在一个 `1u << 6` vs `1u << 12`。这类错误编译器不管、静态检查不管、
   单测不管——真机是唯一的裁判。这也正好是 findings 说的 verifier 主场
   （能力边界附近的语义错误），而本案例里 verifier 差一点就抓到了。
