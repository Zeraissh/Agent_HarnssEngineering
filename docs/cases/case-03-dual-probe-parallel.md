# 真实任务案例 #3 — 双探针并行调试实战（2026-08-05）

**任务**：两块 STM32L151（A 板 ← ST-Link，B 板 ← DAPLink）并行完成"烧录 telemetry
固件 + 三项硬件验收 + 双板对照汇总"。注入式计划：boardA ∥ boardB → join；
子任务级资源标签（`probe-stlink` / `probe-daplink`）使同包子任务真并发——
f8f13b0 特性的实战首秀。执行者/核查者均 deepseek-v4-pro。

## 最终结果（第 4 轮，全绿）

| 步骤 | 结果 | 耗时 | 返工 |
|---|---|---|---|
| boardA（ST-Link） | ✔ 三项验收 PASS | 314.0s | 0 |
| boardB（DAPLink） | ✔ 三项验收 PASS | 187.7s | 0 |
| join（对照汇总） | ✔ 两板逐项一致 | 47.8s | 0 |

**墙钟 361.8s vs 各步和 549.6s → 并行节省 34%**（失败轮曾测得 50%——两步
耗时越均衡节省越高）。三个 verifier 各自独立连板/读报告复核，含"A 板 uptime
初值非零系非首次上电"这类细节的正确辨析。双 OpenOCD 会话（端口 3343/3353）
全程共存，MCP 命名会话 + 每会话独立端口分配经受住实战。

## 四轮才通——每一轮失败都有名有姓

1. **轮1（并行）双败**：执行者没有计时/烧录工具，用 reset/read 循环硬测 uptime
   （reset 恰恰清零 uptime——自我拆台），还幻觉出 `stm32__flash`、
   `stm32__program_flash` 等工具名；A 板 verifier 一度读到垃圾数据。
2. **轮2（串行对照）同败**：排除并发嫌疑——failure 与 concurrency 无关。
3. **根因**：`mcp.json` 连接层白名单是 v0.7 只读化石（13 工具），包层白名单
   只能收窄不能扩回（交集陷阱）；CLI 因连接前改写配置而掩盖了它。
   修复（1bcc567）：连接层 = 各包需求并集（20 工具）。
4. **轮3**：B 板全流程通过（修复生效）；A 板 11 次 start 秒败——**我自己遗留的
   hypo 调试会话攥着 ST-Link**（跨进程探针锁缺失的现行案例）。
5. **轮4**：全绿。

## 三个结构性发现

1. **两层白名单的交集陷阱**（已修）：连接层是能力信任边界，应取包需求的并集；
   领域收窄是包层的职责。宿主直连 mcp.json 时尤其致命。
2. **跨进程探针锁缺失**（stm32-gdb-mcp 需求 #1）：编排器内的资源互斥管不到
   进程之间——本案 hypo 会话、历史上的僵尸 openocd 均属此层。建议 server 按
   探针实例做 OS 级锁，错误从 "init mode failed" 升级为 "probe held by PID x"。
3. **失败形态即证据**：三轮失败的形态各不相同（工具幻觉+自我拆台循环 / 同型
   复现 / 秒败×11），每种形态都精确指向自己的根因层——逐 run 事件留档 +
   服务端日志对照是破案的全部依据。

## 环境保障

实验前双板双转储备份（SHA256 双验），实验后 `program` 烧回 + 全片重转储
哈希逐字节一致——两板均还原为用户 Keil 自编译的 telemetry 固件，无痕退出。
