# 01 — 设计哲学：Harness Engineering

## 核心命题

在模型能力固定的前提下，agent 的表现差异几乎全部来自 harness。同一个 `claude-opus-4-8`，在一个精心设计的 harness 里可以自主完成数小时的工程任务，在一个粗糙的 harness 里连一次文件编辑都做不可靠。差异体现在四个地方：

1. **循环结构（Loop）**——模型什么时候被再次调用、带着什么信息被调用、什么时候停下来；
2. **工具形状（Tools）**——模型能发出什么样的动作，宿主能对这些动作做什么（拦截、审批、渲染、并行调度）；
3. **上下文质量（Context）**——模型每次看到的 prompt 是不是干净、稳定、缓存友好；
4. **验证闭环（Verification）**——模型声称完成的事情，有没有独立机制去核实。

Harness engineering 就是把这四件事当成一等工程问题来做，而不是当成"调 prompt"的附属品。

## 为什么从零手写

现成框架（Claude Agent SDK、LangGraph、各种 agent 框架）把 loop、工具调度、上下文管理都封装好了。用它们能更快出活，但也意味着这些核心决策是别人替你做的。本项目的首要目标是**理解与掌控**：

- 每一层的代码量其实不大（核心 loop 百行以内），复杂度在于**决策**而非实现；
- 自己写过一遍之后，再看任何框架都能一眼看出它在哪一层做了什么取舍；
- 领域接入（如嵌入式调试）往往需要对 loop 和工具层做非标准改造，自研骨架改起来没有黑盒阻力。

## 设计原则

### P1 — 分层可替换

每一层只依赖下一层的接口，不依赖实现。ModelClient 可以换模型、换 provider；工具是纯插件；上下文策略可以独立演进。判断标准：**换掉任何一层的实现，其他层的代码不需要动。**

### P2 — Bash 起步，按需晋升为专用工具

给模型一个 bash 工具，它几乎什么都能做——但宿主拿到的只是一个不透明的命令字符串。把某个动作"晋升"为专用工具的时机，是当你需要以下任意一项时：

- **安全边界**：难以回滚的动作（发消息、删数据、外部 API 调用）需要审批门——`send_email` 工具好拦截，`bash -c "curl -X POST ..."` 拦不住；
- **不变量校验**：专用 `edit` 工具可以拒绝"文件在上次读取后已变化"的写入，bash 做不到；
- **渲染**：某些动作值得专门的 UI（如向用户提问渲染成选项框）；
- **调度**：只读工具可标记 parallel-safe 并行执行；bash 里分不清 `grep` 和 `git push`，只能串行。

反过来说：不需要以上任何一项的动作，留在 bash 里，别为它膨胀工具面。工具太多会稀释模型的选择质量。

### P3 — 上下文是稀缺资源，且缓存是前缀匹配

Prompt caching 的本质是**前缀字节匹配**：渲染顺序为 tools → system → messages，前缀中任何一个字节的变化都使其后的全部缓存失效。由此推出三条铁律：

1. **system prompt 冻结**——绝不在里面插时间戳、会话 ID、模式开关等易变内容；动态上下文放到 messages 末尾注入；
2. **工具列表与模型中途不变**——两者都渲染在最前面，中途增删工具或换模型等于全量重算；
3. **稳定在前、易变在后**——按"永不变 / 会话级 / 轮级 / 请求级"给内容分级，物理排列顺序必须与稳定性排序一致。

### P4 — 默认可观测

每一轮 loop 必须能回答：这轮花了多少 token（区分 cache read / cache write / 未缓存）、调了哪些工具、输入输出是什么、为什么停下来。可观测性不是加日志的事后工程，而是 loop 对外契约的一部分——loop 以**结构化事件流**（AsyncIterable）对外发射，日志、UI、审批门都是事件的消费者。

### P5 — 错误进上下文，而不是炸掉循环

工具执行失败不是异常路径，是常态路径。失败信息以 `is_error: true` 的 tool_result 回传给模型，让模型自己调整策略；只有宿主级故障（API 不可达、预算耗尽）才终止循环。一个好的 harness 里，模型看到的错误信息质量直接决定它的恢复能力——错误信息要写给模型看，不是写给人看。

### P6 — 护栏是宿主的责任，不是模型的自觉

最大轮数、token 预算、危险动作审批——这些约束由 loop 强制执行，不依赖 prompt 里的"请注意不要……"。Prompt 约束是软的，harness 约束是硬的；两者都要有，但安全性只能建立在硬约束上。

## 非目标（v0.x 阶段明确不做）

- 多 provider 抽象（只对接 Anthropic API；P1 保证以后想做时做得动）
- 图式编排 / DAG workflow（先把单 agent loop 做扎实）
- Web UI（CLI 事件渲染够用）
- 插件市场式的工具生态（工具就是仓库里的 TS 模块）
