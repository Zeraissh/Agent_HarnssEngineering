UI / UX TECHNICAL REMEDIATION

Agent Harness Web UI 整改报告

基于实际界面审计、DOM/CSS 检查与同类产品对照

评审对象：Agent Harness — Web UI

评审范围：运行列表、任务创建、运行详情、审批、核查、窄屏布局

审计视口：951×831 桌面窗口；390×844 窄屏窗口

报告日期：2026-08-06

文档状态：V1.0 · 待评审

总体结论  当前界面已经具备工程控制台的基本骨架，但状态冲突、结果被日志淹没和窄屏不可用会直接削弱可信度与可操作性。建议先修正状态与审批逻辑，再重构详情页信息层级，最后统一视觉与效率功能。

1. 执行摘要

本报告将问题分为 P0、P1、P2 三个等级。P0 是正确性、安全性或核心可用性问题，属于发布阻断项；P1 是核心效率与无障碍问题，应在下一迭代完成；P2 是视觉一致性和长期使用效率优化。

P0：已完成运行仍保留可操作审批；390px 窄屏下核心详情被固定侧栏挤压。

P1：最终结果位于长日志之后；原始日志缺乏分层；空状态、文案和键盘语义不完整。

P2：核查区视觉权重过高；运行列表缺少时间、耗时与结果差异；设计令牌尚未统一。

建议决策  按“状态模型与审批 → 响应式框架 → 结果优先详情 → 日志分层 → 无障碍与视觉统一”的顺序实施。在 P0 问题关闭前，不建议将当前界面作为稳定生产控制台发布。

2. 审计范围与证据边界

审计基于 2026-08-06 当日可访问的本地页面及现有三条已完成运行记录，覆盖以下操作路径：

打开运行列表并观察未选择运行时的初始状态。

选择历史运行并查看审批卡、主时间线和独立核查区域。

滚动查看最终结果、核查结论和人工复核提示。

在 390×844 窄屏条件下检查布局可用性。

检查关键 DOM/CSS 语义，包括列表焦点、输入标签、状态播报、媒体规则和实际颜色值。

证据限制：当前样本主要是已完成运行，未完整覆盖运行中、等待输入、执行失败、取消和网络异常等动态状态；本次也未执行完整屏幕阅读器、200% 缩放和后端状态机审计。因此报告中的无障碍和状态机结论应作为整改基线，并在实施后通过专项测试闭环。

4. 当前设计的可保留部分

深色中性色底与有限强调色符合工程工具和长时间运行监控场景。

“运行列表—运行详情”的基础导航模型正确，适合并行任务管理。

把主 Agent 与独立核查 Agent 分开呈现，有助于建立过程透明度。

允许、拒绝、通过、待复核已经具备初步状态色语义，可在统一状态模型后保留。

5. 界面证据：初始状态

左侧已经存在三条已完成运行，但右侧仍显示“尚无运行”。这会让用户误以为系统没有历史记录，也无法判断下一步应该选择运行还是创建任务。

图 1  初始状态：运行列表已有记录，但详情区提示“尚无运行”

观察结论  空状态应区分“列表为空”和“尚未选择运行”。建议文案改为“选择左侧运行查看详情，或创建新任务”；按钮“提交”改为“运行任务”，“核查”改为“开启独立核查”。

6. 界面证据：历史运行详情

历史运行标题和状态显示为“已完成”，但顶部仍存在可点击的“允许/拒绝”操作。这是本次审计中优先级最高的状态一致性问题。

图 2  历史运行详情：完成状态与可操作审批卡并存

观察结论  仅当审批状态为“待处理”时显示审批动作。已处理审批应在对应时间线中显示为只读记录，至少包含动作、对象、决策、处理主体和时间；完成、失败或取消运行不得出现可执行审批控件。

7. 界面证据：结果位于日志之后

用户需要滚动经过多轮 JSON、工具调用和核查日志后，才能看到完成摘要、核查通过和待委托方复核信息。核心结果不应依赖阅读原始日志才能理解。

图 3  结果区：最终结论位于长日志下方

观察结论  默认详情页应先显示最终状态、结果摘要、变更/产物、验证结论和下一步；原始日志通过“运行日志”标签或折叠区按需查看。失败、异常和待审批步骤自动展开，成功步骤默认折叠。

8. 界面证据：390px 窄屏

窄屏下仍保留 280px 左侧栏，导致详情标题、审批卡和日志被压缩到不可阅读宽度。该问题会阻断移动端和分屏场景的核心任务。

图 4  390×844 窄屏：详情区被固定侧栏挤压

观察结论  390px 下改为单栏流程：运行列表与详情分层显示；进入详情后提供返回列表；主流程与核查改为标签页或抽屉。390、768、1280、1440 四个视口均应纳入回归测试。

10. 建议的目标信息架构

建议保留两层导航，但将详情页从“日志容器”重构为“任务结果与控制中心”：

运行列表：支持搜索、状态筛选和时间分组；显示标题、状态、开始时间/耗时和核查结论。

详情页头：显示标题、状态、耗时和随状态变化的唯一主操作；任务输入区分“创建新任务”和“追加指令”。

概览：默认展示结果摘要、变更/产物、验证结论、风险、下一步和需介入事项。

产物/变更：集中展示文件、diff、截图和测试结果。

运行日志：按轮次/步骤折叠，以“动作 + 对象 + 结果 + 耗时”摘要，原始参数/输出二级展开。

核查：先呈现结论与关键证据；过程作为次级详情。

审批：待处理时显示首屏高优先级卡片；处理后保留只读记录。

11. 分阶段整改方案

阶段一：关闭 P0 发布阻断项

建立运行、审批、核查三类独立状态及合法转换表，所有界面统一读取同一状态源。

仅在待审批状态显示允许/拒绝；为提交动作增加幂等保护；历史审批改为只读记录。

完成单栏窄屏架构，移除固定侧栏造成的详情挤压。

覆盖已完成、失败、取消、等待审批、审批拒绝等状态组合的自动化测试。

阶段二：完成 P1 核心体验整改

上线“概览—产物/变更—运行日志—核查”四层详情结构。

将日志改为摘要卡；成功默认折叠，失败、异常和待审批默认展开。

修正空状态、加载、失败、离线和权限不足等反馈文案。

将运行项改为可聚焦语义控件，补充 aria-selected、正式输入标签、aria-live 和可见焦点。

修正对比度；正文建议不低于 14px，辅助信息建议不低于 12px。该字号为本项目可读性建议，不是 WCAG 的直接阈值。

阶段三：落实 P2 视觉与效率优化

建立统一颜色、字号、间距、圆角和状态令牌，减少硬编码。

收敛核查区紫色面积，保持主结果的最高视觉权重。

增加运行筛选、长日志搜索、失败/待审批快速跳转和日志导出。

建立结果定位耗时、审批处理耗时、重复提交和状态冲突等体验指标。

排期说明  本报告给出实施顺序而非固定工期。具体排期取决于现有前端框架、后端状态结构、自动化测试基础和产品交互决策；进入开发前应由产品、前端、后端与测试共同确认依赖和负责人。

14. 发布门槛

P0 项全部关闭，状态冲突、历史审批可操作和窄屏核心流程不可用问题为 0。

桌面端与移动端核心流程测试通过率为 100%。

自动化无障碍扫描中 Critical 和 Serious 问题为 0，并完成键盘与屏幕阅读器人工验证。

审批重复提交率为 0，非法状态组合不得渲染可执行操作。
